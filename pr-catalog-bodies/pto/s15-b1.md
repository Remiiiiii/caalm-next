## Tasks (Who / What / Where / Why / When / How)

### 15.1 preview_mutation

- **Who:** All assistant users
- **What:** Show a before/after preview before any confirm
- **Where:** shared helper used by mutating tools
- **Why:** Preview builds trust and prevents mistakes
- **When:** Agent OS batch
- **How:** Read-only preview; no write until confirm

**Done when**
- preview_mutation renders before/after for a pending action without writing
- Mutating tools can call it ahead of confirm

### 15.2 undo_last_action

- **Who:** Users who performed the action
- **What:** Reverse the last action where the product is safely reversible
- **Where:** wrap reversible writes only
- **Why:** Reversibility is expected of governed agents
- **When:** Agent OS batch
- **How:** Only safe, reversible actions; confirm; audit the undo

**Done when**
- undo_last_action only offers reversal for actions the product can safely reverse
- The undo is confirmed and audited; irreversible actions are refused with a clear message

### 15.3 explain_why_denied

- **Who:** Any user who hits a permission wall
- **What:** Explain which permission is missing and who to ask
- **Where:** shared RBAC explainer
- **Why:** Turns a blunt 403 into a next step
- **When:** Agent OS batch
- **How:** Read-only; names the permission in plain English; never bypasses it

**Done when**
- explain_why_denied maps a missing permission to a plain-English reason and an admin to ask
- It never grants or bypasses the permission

### 15.4 list_my_capabilities

- **Who:** All assistant users
- **What:** Answer 'what can you do for me?' from the user's permitted tools
- **Where:** read the tool registry filtered by permissions
- **Why:** Discovery of safe actions
- **When:** Agent OS batch
- **How:** Read-only; reflects getToolsForPermissions for the caller

**Done when**
- list_my_capabilities lists only tools the caller's permissions allow
- No tool outside the user's permissions is suggested

### 15.5 compose_skill_multi_step

- **Who:** All assistant users
- **What:** Compose existing tools into a named multi-step skill (e.g. onboard vendor = create contract + tasks + approval)
- **Where:** orchestrate existing ToolDefinitions only
- **Why:** Reusable skills are the top of the agent ladder
- **When:** Agent OS batch
- **How:** Each underlying tool keeps its own permission, confirm, and audit; no new agent runtime (no-workflow-engine-sprawl)

**Done when**
- compose_skill_multi_step only chains existing permission-gated tools and confirms each mutating step
- No second workflow/agent engine is introduced
