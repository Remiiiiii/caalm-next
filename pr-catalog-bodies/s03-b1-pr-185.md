## Tasks (Who / What / Where / Why / When / How)

### 3.1 Session-bound two-factor setup

- **Who:** Every user turning on two-factor
- **What:** 2FA setup and verify only work for the logged-in user — no passing someone else's user id in the body
- **Where:** src/app/api/2fa/setup, verify, status
- **Why:** Letting callers pick a user id is account takeover bait
- **When:** After API coverage section
- **How:** getCurrentUser required; reject body userId mismatch; remove from unguarded baseline

**Done when**
- Unauthenticated setup returns 401
- Cannot enable 2FA for another user's id

### 3.2 Remove test-only 2FA from production

- **Who:** Security and IT
- **What:** Test and debug 2FA routes are disabled or blocked outside development
- **Where:** 2fa/test, test-totp, similar debug paths
- **Why:** Pen testers flag open test endpoints immediately
- **When:** Same PR as 3.1
- **How:** NODE_ENV guard or delete routes; baseline entries removed

**Done when**
- Production build cannot reach test 2FA endpoints
- Development still can exercise flows locally

### 3.3 Audit log on session revoke

- **Who:** Compliance and IT admins
- **What:** When a session is revoked, write a clear audit event who did it and for which user
- **Where:** auth session revoke flows, audit log writer
- **Why:** Buyers ask who forced logout during an incident
- **When:** After 3.1
- **How:** Hook existing revoke; use same audit schema as other security events

**Done when**
- Revoke produces a row visible in audit log UI
- Event includes actor and target user

### 3.4 Audit log on password and 2FA reset

- **Who:** Compliance and IT admins
- **What:** Password change and 2FA reset actions appear in the audit trail
- **Where:** user security settings APIs
- **Why:** Pairs with session revoke for a complete security story
- **When:** Same section PR or follow-up
- **How:** Same pattern as 3.3

**Done when**
- Reset events show in audit filters
- No silent security changes
